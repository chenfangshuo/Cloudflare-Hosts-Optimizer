# 工作原理

## 目标

不是"找出延迟最低的 CF IP"，而是"找出对这些域名实际最快、且确实能用的边缘 IP"，
并且以可回滚、不破坏 hosts 其他内容的方式落地。

## 流程

1. **延迟/丢包筛选**
   - 有 `cfst.exe`：`cfst -dd -tlr 0.05`，只做延迟/丢包，不做下载测速。
   - 没有：内置扫描，从 Cloudflare 官方 IPv4 段随机抽样，用
     `speed.cloudflare.com/cdn-cgi/trace` 探测。
   - 只保留丢包率 ≤5%、有响应的 IP，按延迟升序。
   - 两条路径共用后续所有步骤；覆盖与测量方式的差异见 README 的对比表。
   - CFST 的输出写到本次运行独立的临时目录，不覆盖用户已有的 `result.csv`；
     数字用 `InvariantCulture` 解析，并校验丢包/延迟范围和 IP 是否属于允许网段。

2. **机房探测与分层抽样**
   - 取延迟最低的 256 个候选，逐个读取 `colo=`。
   - 按机房分组，组内按 TTFB 排序，再轮流取样 32 个。
   - 目的：避免纯延迟排序把候选全选成 HKG。HKG 握手可能很快，但大流量丢包严重。

3. **吞吐初测**
   - 对 32 个候选请求 `-SpeedTestUrl`，每个 1MB。
   - 有效样本必须同时满足：
     - curl 退出码 0；
     - HTTP 200 或 206；
     - 下载字节 ≥ 请求字节的 95%；
     - `time_total > 0`；
     - `remote_ip` 等于候选 IP（`--resolve` 生效）；
     - 不跟随重定向（`--max-redirs 0`）。
   - 初测只用于晋级，不作为最终成绩。

4. **决赛**
   - 初测吞吐前 6 名进入决赛：3 次 × 2MB，**串行**（避免 6 条下载互相抢本机带宽）。
   - 有效样本 ≥2 才参与排名；取真中位数（偶数个取中间两值平均）。
   - 决赛失败的 IP 直接淘汰，**不保留初测分数**。
   - 最终排名只使用决赛成绩。

5. **逐域名选择（基线对比）**
   - 基线：对该域名发 1 次不带 `--resolve` 的 `HEAD`，走系统当前的 hosts/DNS 路径。
   - 候选：全局决赛前 K 个（`-CandidatesPerDomain`，默认 3）+ 该域名的旧映射，去重。
   - 前 K 个都不可用时，补测 `-BackfillCandidates` 个（默认 1）；每域名候选探测
     受 `-MaxDomainProbes`（默认 6）约束。
   - 每个候选都是带 `--resolve` 的 `HEAD`；403/503 会额外发 1 次小 GET
     （`Range` + `--max-filesize 65536`，只读前 16KB）识别 1034/1003。
   - 所有时间字段都扣掉 `time_namelookup`：候选走 `--resolve`（解析≈0），
     基线走系统解析；不扣掉的话基线会白背一次 DNS 时间，门槛会被解析时间吃掉。
   - 准备切换且基线可用时，切换前复核：基线与**选中的那个候选**各复测一次并取中位数，
     只在这两者之间比较，不在全部候选里重选；候选复测失败/受限则不切换。
     这也是每域名每 IP 最多 2 次 HEAD 的来源（首次验证 + 一次复核）。
   - 切换条件：百分比 ≥ `-MinImprovementPct`（默认 15%）**且**绝对改善
     ≥ `-MinImprovementMs`（默认 30ms），或基线失败/类别更差。
     快基线下 15% 可能只有十几毫秒，绝对门槛用来挡住噪声。
   - 如果基线或候选中出现 1034 且没有可用候选，再解析该域名自己的 DNS A 记录
     （`-NoHostsFile`，最多 2 条，仅接受 IPv4 且在允许的 CF 网段内）。
   - 选择：2xx/3xx/401 优先于 403；未达门槛时保留基线，不写 hosts。
   - 旧映射：只有明确 1034/1003 才自动丢弃；连接失败默认保留并告警，
     `-DropUnreachable` 才删除。
   - 每个域名最多写 `-TopN` 个 IP（默认 1）；多 IP 时额外 IP 需与主 IP 同类且
     TTFB 不超过主 IP 的 1.5 倍。

6. **写入 hosts**
   - 读取并严格解析；任何结构/编码/冲突问题都直接中止。
   - 增量合并：成功 → 更新；失败 → 保留旧映射（仅 1034 自动丢弃；连接失败默认保留，
     `-DropUnreachable` 才删除）；不在列表 → 默认保留，`-Prune` 才删除。
   - 备份 → 临时文件 → 原子替换 → 读回校验 → 刷新 DNS。

## 关键设计决策

### 为什么 CFST 只做延迟，不做下载测速

CFST 的测速结果高度依赖 `-url` 指向的文件。官方默认地址 `https://cf.xiu2.xyz/url`
在某次实测中返回 **403**，CFST 会把 403 响应体当成"下载完成"，算出 15 MB/s 之类的假速度；
独立用 3MB 文件复测，真实吞吐只有 0.48 MB/s。

这是一个特定时间/网络下的观测，不保证所有环境复现。但结论是通用的：
**不要把单一测速端点的结果当成真实吞吐**。本工具只使用 CFST 的延迟/丢包能力，
吞吐量自己测，并校验完整性和实际远端 IP。

### CFST 与内置扫描

`cfst\` 里有 `cfst.exe` 时优先用 CFST；没有、运行失败或指定 `-NoCfst` 时用内置扫描。
两者**共用**后面的机房分层、吞吐决赛和逐域名基线选择，区别只在“候选 IP 池”和
“延迟测量方式”。

| | 有 cfst.exe（默认优先） | 内置扫描（`-NoCfst` / 未找到） |
|---|---|---|
| 候选来源 | `cfst\ip.txt`：当前 25 个网段 | 从官方网段随机抽 `-MaxCandidates` 个（默认 192） |
| 延迟测量 | TCPing（TCP RTT） | HTTPS `cdn-cgi/trace`（含 TLS，接近网页 TTFB） |
| 覆盖 | 更广，通常更容易找到低延迟、低丢包的 IP | 抽样有限，可能漏掉好 IP |
| 速度 | CFST 内部多线程，扫描快 | 192 × 2 次 curl，通常几十秒 |
| 依赖 | 第三方 GPL-3.0 二进制，需自行下载 | 仅 PowerShell 7 + 系统 `curl.exe` |
| 相关参数 | `-CfstPath` | `-MaxCandidates`、`-ScanSamples`、`-NoCfst` |

- 两者都只做**延迟/丢包预筛**；最终选哪个 IP 由吞吐决赛 + 逐域名基线决定。
- CFST 的下载测速不使用（它的默认测速地址可能返回 403），只用 `-dd`。
- 内置扫描的覆盖取决于 `-MaxCandidates`；觉得效果差可以调到 384/512，代价是时间。
- 两条路径都只允许 CF 官方网段；`104.28.0.0/14` 需要 `-ExperimentalRanges`
  （CFST 的 `ip.txt` 虽包含它，也会被过滤）。
- CFST 找不到或运行失败会自动回退，不会中断。
- 批量扫描只打 Cloudflare 公共端点；对 PT 站的 HEAD 验证是另一阶段，和选哪条扫描路径无关。

### 为什么按机房分层

同一线路到不同 CF 机房的表现差异很大：

- HKG：TCP 握手可能只有 130ms，但大流量丢包、TLS 偶发数秒、3MB 下载可能超时。
- LAX/SJC：握手 170–340ms，吞吐不一定最好，但通常更稳定。
- FRA/LHR 等：有时吞吐反而更高，但网页 TTFB 不一定更好。

只按延迟排序会系统性地高估 HKG。分层抽样保证每个主要机房都有候选，
再由吞吐和逐站 TTFB 决定。

### 为什么逐域名验证

同一个 CF 边缘 IP 能服务任何 CF 站点，但站点本身可能：

- 不是 Cloudflare 托管；
- DNS 被污染（必须靠 hosts，但错误的 IP 同样打不开）；
- 正在维护或 WAF 拦截；
- 对 HEAD 请求直接断开。

逐站验证是最后一道保险。验证失败时保留可用旧映射，不会把原本能用的站弄挂。
需要强调：这是"尽力而为"，不是"非 CF 一定能识别"。

### 为什么逐域名 + 基线对比

- 同一个全局 IP 可能对 A 站可用、对 B 站返回 1034；不同站点到不同机房的 TTFB 也不同。
  所以全局吞吐排名只用于挑出前 K 个候选（`-CandidatesPerDomain`，默认 3），
  最终由每个域名独立选择。
- 基线 = 该域名当前的 hosts/DNS 路径。只有候选比基线快 ≥ `-MinImprovementPct`
  （默认 15%）且绝对改善 ≥ `-MinImprovementMs`（默认 30ms），或基线失败/类别更差时
  才切换，并在切换前基线与候选各复核一次。这样避免在测量噪声范围内频繁改写。
- 请求预算：每域名 1 次基线 + K 次候选 + 补位 + 旧映射 + 最多 2 次 DNS 回退
  + 切换前复核 2 次；`-MaxDomainProbes`（默认 6）限制候选探测，典型约 6–10 次、
  最坏 11 次 HEAD。403/503 额外 1 次 ≤64KB 的诊断 GET。
  仍然不登录、不带 Cookie、不访问 announce。
- 对返回 1034 的 zone，这仍然只能在它允许的 IP 里选；不会突破服务端白名单。

### 为什么 DNS 回退赢了也不写 hosts

1034（Edge IP Validation）表示这个 zone 只服务它自己的 IP（BYOIP、专属/静态 IP、
SaaS 接入等），本质上无法优选。这时 DNS 回退找到的 IP 只是"当前"可用；
写进 hosts 会在站点换 IP 后变成故障源，而且下次运行只会被当成连接失败而继续保留。
所以胜出的候选 `Source = 'dns'` 时，动作是**交还 DNS**（删除该域名的托管条目），
让系统解析始终拿到最新地址。BYOIP 地址不在 CF 公共网段里，会被过滤掉，
这种情况下通常连 DNS 回退都没有——结果同样是交还 DNS。

注意：工具只删除自己托管区块里的条目。如果 hosts 区块外还有该域名的旧条目
（早先被注释的原条目会恢复，用户手工行会保留），它们仍会生效；运行结束时会告警，
需要真正交还 DNS 时请手动删除或注释这些行。

### 为什么写 A 记录会让浏览器走 IPv4

在 Windows 上，hosts 里存在的 A 记录通常会让系统解析器不再从 DNS 返回该名字的 AAAA，
因此浏览器会使用 hosts 里的 IPv4。

但这不是绝对的：应用自带解析器、DoH、缓存等可能有不同行为。`-CheckResolved`
可以查看系统实际返回的地址。

这只影响这些域名的网页/tracker；BitTorrent 的 IPv6 对等连接不受影响。

### 为什么默认不做 IPv6 优选

在测试线路上，CF 的 IPv6 全部落到 LAX，3MB 下载 15 秒只收到 1.25MB（约 83KB/s），
明显差于 IPv4 候选。脚本目前只扫描 IPv4。

## hosts 写入算法

- 只用一对标记界定管理范围。
- 标记结构必须合法：0 对或恰好 1 对，BEGIN 在 END 之前；否则中止。
- 受管域名的旧条目改成 `# [pt-cf-optimize] <原内容>`，不删除。
- 多别名行、IPv6 映射、其他工具的托管区块（例如 `# S302 BEGIN/END`）→ 中止。
- 编码只支持 ASCII / UTF-8（含 BOM）；UTF-16、GBK 等 → 中止。
- 增量合并，重复运行幂等。
- 非管理行保持原样；区块固定放在末尾，前后空行会被规范化。

## 事务与回滚

- 全局互斥锁 `Global\pt-cf-optimize`。
- 提交前重新读取 hosts，哈希与开始时不一致 → 中止。
- 备份目录：`%ProgramData%\pt-cf-optimize\backup`（不可写时回退项目目录）。
  非系统 `-HostsPath` 使用 `targets\<路径哈希>` 子目录；回滚时还会校验 manifest 的
  `hostsPath`，避免沙箱备份被系统 hosts 的回滚选中。
- 备份名：`hosts-<yyyyMMdd-HHmmss>-<8位GUID>.bak`，附 JSON 清单（pre/post 哈希）。
- 按**文件名**选最近备份，不依赖 LastWriteTime（复制文件会保留源文件的修改时间）。
- 写入：临时文件 → 读回校验 → `File.Replace` 原子替换 → 再读回确认。
- 回滚：当前 hosts 哈希与清单 `post-hash` 不一致时默认拒绝，`-Force` 才覆盖。

## 局限

- 只支持 Windows（依赖 HKCU 代理设置、`Get-NetAdapter`、`ipconfig`）。
- 只做 IPv4。
- CF 路由和运营商互联会变化，结果有时效性。
- 吞吐测速有噪声；多次采样和中位数只能降低误判，不能消除。
- 逐站验证只发 HEAD，不保证登录、发种、下载等功能一定正常。
- 无法完整识别透明代理/TUN/WFP；只能检查已知信号。
